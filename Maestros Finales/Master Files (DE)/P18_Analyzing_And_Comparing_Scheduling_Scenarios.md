## Identifying which scenarios you're going to compare

After creating, calculating, validating, and publishing scenarios, the next natural step is to compare them. Comparing scenarios is not just to see which “was best” intuitively. It consists of reviewing what changed, what impact that change had, and whether the new iteration actually improves the reference solution.

Use this quick start when you already have at least two comparable scenarios, for example a published solution and a new calculated iteration, and you need to decide which one should be retained as an operational reference or which one deserves to advance in the life cycle.

Before you start, make sure that:
1. You've already created and calculated at least one base scenario.
2. You already have a second version, iteration or variant that you want to compare.
3. You know what line, what kind of day and what operational context you're reviewing.
4. You're clear what the current reference version is.

For this quick start, use this reference case:

> **I'm going to compare the published scenario of line L1 with a new iteration calculated to decide if the new solution actually improves the current programming.**

To correctly identify the scenarios to be compared:
1. In GoalBus, open the **Planning scenarios** module.
ref: P18_Imagen1.png | compact
2. Locates the scenario that acts as the current reference.
3. Locate the new scenario or iteration you want to evaluate.
4. Checks that both scenarios belong to the same functional context:
   1. the same line or comparable set of lines,
   2. same type of day,
   3. same general operational logic.
5. Check the name, description and status of each scenario.
6. Confirms which is:
   1. the current or published version;
   2. and what is the new proposal.
7. If the scenarios are not comparable to each other, do not continue to correct that point.

For the reference case, make sure that:
1. Both scenarios belong to line L1.
2. Both are working or respond to the same time context.
3. One acts as a reference and the other as an alternative.

When you finish this section, you should have clearly identified the scenarios you're going to compare and the role that each plays.

## Reviewing KPI, workload and overall balance

Once the scenarios are selected, you need to start with a high-level comparison. Here the goal is to review general indicators before going into task details or rules. This first comparison helps you detect whether the new solution is actually better balanced or whether it only changes the result without bringing real value.

Before starting this section, make sure that:
1. You know what two scenarios you're going to compare.
2. You've already identified the reference.
3. You already have access to visible stage KPIs or comparable metrics.

To review the general KPI scenarios:
1. Opens the first stage and reviews its main KPIs.
2. Note or remember at least:
   1. total workload,
   2. number of tasks,
   3. total time,
   4. relevant operational distance or magnitude,
   5. any other indicator visible in the interface.
3. Open the second stage and check the same KPIs.
4. Compare if the new iteration:
   1. reduces unnecessary complexity,
   2. improves balance,
   3. or displaces the problem from one place to another.
5. Avoid a good iteration just because it changes the numbers. The important thing is that the change makes operational sense.

For the reference case, ask yourself:
1. Does the new iteration reduce unnecessary tasks?
2. Does the overall balance seem more reasonable?
3. Is the total volume still consistent with the validated offer?
4. Is the improvement real or is it just a redistribution with no clear benefit?

When you finish this section, you should have a global reading of whether the new solution deserves a deeper review.

## Comparing impact on vehicles and shifts

After reviewing global KPIs, you need to go down to functional logic. In this phase, the comparison must separate two things:
1. the impact on **vehicles**,
2. and impact on **shifts**.

This is important because an iteration can improve the logic of the fleet and worsen the logic of shifts, or the other way around. If you mix both dimensions, the reading becomes confusing.

Before starting this section, make sure that:
1. You've already checked the general KPIs.
2. You know what vehicle and shift rules are involved in the change.
3. You're already clear on the purpose of the iteration.

To compare the impact on vehicles:
1. Check how the solution behaves with respect to:
   1. fleet used,
   2. compatibilitys,
   3. departures from warehouses or parking spaces,
   4. and non-productive mileage, whether visible or deductible.
2. Check whether iteration improves consistency between line, fleet and infrastructure.
3. It detects whether the new scenario forces solutions that were previously more realistic.

To compare the impact in shifts:
1. Check how tasks or work blocks are built.
2. Check if active shift types still make sense.
3. See if the new solution:
   1. improves the clarity of work,
   2. worsens the structure,
   3. or introduce unnecessary rigidities.
4. Related the change to the shift rule model you've used.

For the reference case, ask yourself:
1. Does the new iteration improve the logic of vehicles without punishing the logic of shifts?
2. Does shift logic improve without making the fleet worse?
3. Which of the two dimensions wins or loses?
4. Is the overall result more robust or just more different?

When you finish this section, you should understand where each scenario gets better and where it gets worse.

## Deciding whether the new iteration brings real value

Now you need to turn the comparison into a decision. Not every new scenario deserves to move forward. Sometimes a new iteration only serves as internal learning and the best decision is to keep the current version. Other times the improvement is clear enough to justify a new cycle of validation and publication.

Before continuing, make sure that:
1. You've already compared general KPIs.
2. You've already checked on vehicles and shifts.
3. You know what the original goal of the new iteration was.

To decide whether iteration brings real value:
1. It summarizes mentally what the purpose of the new scenario was.
2. Check whether that objective was clearly achieved.
3. Ask yourself if the improvement is:
   1. operationally visible,
   2. technically defensible,
   3. and stable enough to keep moving forward.
4. If the iteration clearly improves the reference, prepare it for validation or publication as appropriate.
5. If iteration does not improve the reference, keep it as learning and keep the current version.
6. Do not promote an iteration just because it is newer. Promote it only if it is better for the case.

For the reference case, finish this section only when you can affirm one of these two things:
1. The new L1 iteration clearly improves the published solution and deserves to move forward.
2. The published solution remains the best reference and the new iteration remains as an analysis.

When you finish this section, you should have a clear and justifiable decision about which scenario should be retained as a reference.

## Leaving comparison traceability for future iterations

The last step is to leave a trace of the comparison. Comparing scenarios without leaving traceability forces to repeat the analysis in the future and makes it more difficult to explain why a version was promoted or discarded.

Before you finish, make sure that:
1. You've already made a decision on the stage.
2. You know what's left for reference.
3. You're clear what the main reason for the decision was.

To leave comparison traceability:
1. Check the name and description of both scenarios.
2. If necessary, update the description of the new scenario to better reflect its purpose or outcome.
3. It retains identified the reference version as:
   1. published,
   2. validated,
   3. or maintained as an official base.
4. Keep iteration not promoted as a comparative reference if it brings historical value.
5. If your internal process requires it, record what changed between the two scenarios and why the final decision was made.

For the reference case, make sure that:
1. You can explain why the new scenario does or does not improve to current L1.
2. The decision is reflected in names, descriptions or internal process.
3. The next iteration, if it exists, will not start from confusion.

When you finish this section, you should have not only a comparison made, but a traceable and useful decision for future iterations.
